## 文档说明

本规范是DSH软件工程智能协同平台的**全局基线研发标准**，对应底层`common_specs/`全局公共开发规范库，是全机构所有软件研发项目必须遵守的最低执行标准，也是七大领域智能体执行任务的核心依据与输出校验准则。
本规范向下兼容项目级定制规范，项目专属规范不得低于本规范设定的基线要求；本规范同时作为智能体代码生成、质量评审、测试验证等能力的内置校验标准，确保智能体输出符合统一研发要求。

## 第一部分 总则

### 1\.1 编制目的与背景

为支撑企业级多团队、多项目并行软件研发的协同化与智能化转型，统一研发标准、保障代码质量、沉淀研发资产、强化安全合规，充分释放DSH（DeepSeek Harness）智能体技术的生产效能，构建全流程可追溯、可度量、可复用的软件工程体系，特制定本规范。

### 1\.2 适用范围

本规范适用于全机构所有基于DSH软件工程智能协同平台开展的软件研发项目，覆盖需求调度、需求分析、代码开发、质量评审、测试验证、部署执行、运维保障七大研发全生命周期领域，适用于所有研发、测试、运维、质量管理人员及DSH智能体执行过程。

### 1\.3 规范层级体系

本规范为DSH研发规范体系的**全局统一基线**，整体规范体系分为三级，自上而下约束强度叠加：

1. **全局统一规范**（本文件）：全机构强制执行的最低标准，对应底层`common_specs/`目录，所有项目必须遵守，不得突破基线要求

2. **领域专用规范**：针对七大研发领域的补充细化标准，对应领域通用配置，在全局规范基础上进行领域专项约束

3. **项目专属规范**：单项目定制化细则，对应项目级`specs/`目录，可在不低于全局基线的前提下进行项目级扩展

### 1\.4 核心执行原则

- **配置即代码**：所有研发规则、流程标准均以可配置化方式落地，纳入版本管理，支持智能体读取执行

- **校验前置**：所有代码提交、配置变更、产物交付前必须经过规范校验，不合格项禁止进入下一环节

- **全流程可追溯**：研发全链路操作留痕、过程可查、责任到人，支持项目级全维度审计

- **最小权限**：研发环境、系统资源、数据访问均遵循最小权限原则，严控风险边界

## 第二部分 研发全流程领域规范

本部分对应DSH七大领域智能体的执行标准，明确各研发环节的核心规则与输出要求。

### 2\.1 需求调度领域规范（Dispatch）

1. 需求输入必须包含业务背景、目标描述、验收标准、优先级标记四要素，禁止模糊性需求直接进入调度环节

2. 智能任务拆解必须输出标准化任务清单，包含任务名称、所属领域、优先级、依赖关系、预估工时、负责人字段

3. 任务优先级划分为P0（阻塞）、P1（紧急）、P2（重要）、P3（普通）四级，同优先级任务按依赖关系排序执行

4. 需求变更必须提交变更申请，经项目经理审批后重新触发任务拆解，禁止私下调整任务范围

### 2\.2 需求分析领域规范（Requirement）

1. 需求文档必须采用标准模板编制，包含功能需求、非功能需求、业务流程、接口需求、数据需求章节

2. 需求评审必须覆盖完整性、一致性、可行性、可测试性四个维度，评审通过后方可进入开发阶段

3. 需求基线冻结后变更必须走正式变更流程，留存变更记录与影响评估报告

4. 需求条目必须建立唯一标识，实现从需求到任务、代码、测试用例的全链路追溯

### 2\.3 代码开发领域规范（Development）

1. 代码开发必须遵循本规范第三部分技术栈统一标准，智能体生成代码必须通过规范校验后方可交付

2. 代码提交必须关联对应任务ID，提交信息符合统一格式要求

3. 严格遵循组件化、模块化开发原则，公共能力必须沉淀为通用组件，禁止重复开发

4. 代码完成后必须经过本地编译、单元测试、规范扫描三项自检，方可提交合并申请

### 2\.4 质量评审领域规范（Quality）

1. 代码评审实行“必审\+抽审”结合机制，核心代码100%评审，非核心代码按比例抽审

2. 缺陷分级为致命、严重、一般、轻微四级，致命与严重缺陷未修复禁止合并代码

3. 静态代码检查必须纳入流水线门禁，检查不通过禁止构建

4. 智能体质量评审输出必须明确缺陷位置、问题描述、修复建议、严重等级四项核心信息

### 2\.5 测试验证领域规范（Test）

1. 测试分为单元测试、集成测试、系统测试、验收测试四级，各级测试覆盖率必须达到对应阈值

2. 测试用例必须覆盖正常场景、异常场景、边界场景，核心流程用例100%覆盖

3. 缺陷必须按标准流程提交、指派、修复、验证、关闭，留存完整处理记录

4. 智能体自动生成的测试用例必须经过人工审核，确认覆盖性与有效性后方可执行

### 2\.6 部署执行领域规范（Deployment）

1. 环境分为开发环境、测试环境、生产环境三类，环境间配置隔离、数据隔离

2. 部署必须通过标准化流水线执行，禁止手动直接操作生产环境

3. 生产环境发布必须执行灰度发布策略，按比例放量，监控异常即时回滚

4. 部署前必须通过环境一致性校验，部署后必须执行冒烟测试验证可用性

### 2\.7 运维保障领域规范（Operation）

1. 日常运维操作必须走标准化流程，核心操作必须双人复核

2. 监控告警必须覆盖系统资源、应用性能、业务指标三个维度，告警分级响应

3. 故障处理遵循“先恢复、后排查”原则，留存完整故障记录与根因分析报告

4. 变更操作必须提交变更申请，经审批后方可执行，禁止未经授权的生产环境变更

## 第三部分 技术栈统一规范

本部分为全机构统一技术栈标准，对应底层`common_specs/`目录下的技术分类规范，是代码开发、智能体代码生成的强制执行标准，共包含四大技术方向。

### 3\.1 后端开发规范（Go 语言）

#### 3\.1\.1 工程结构规范

采用标准分层架构，项目目录结构统一为：

```Plaintext
project-root/
├── cmd/          # 应用入口
├── internal/     # 内部业务代码
│   ├── handler/  # 接口处理层
│   ├── service/  # 业务逻辑层
│   ├── repo/     # 数据访问层
│   ├── model/    # 数据模型
│   └── pkg/      # 内部公共包
├── pkg/          # 外部可引用公共包
├── configs/      # 配置文件
├── scripts/      # 脚本文件
├── test/         # 测试文件
└── docs/         # 项目文档
```

禁止跨层调用，禁止循环依赖，公共能力必须沉淀至`pkg`或`internal/pkg`层。

#### 3\.1\.2 编码规范

1. 遵循Go官方编码规范，使用`gofmt`格式化代码，启用`golangci-lint`静态检查

2. 命名采用驼峰命名法，包名小写、见名知意，禁止下划线包名；导出函数必须添加注释

3. 错误处理必须显式处理，禁止忽略错误返回；错误信息必须包含上下文，便于定位问题

4. 禁止全局变量滥用，依赖注入方式管理对象生命周期；并发编程必须做好资源控制与锁机制

#### 3\.1\.3 接口设计规范

1. RESTful API 设计遵循资源导向原则，URL使用名词复数，HTTP方法对应操作类型

2. 统一响应结构体，包含`code`（状态码）、`message`（提示信息）、`data`（响应数据）、`trace_id`（链路ID）字段

3. 错误码统一规划，按业务领域划分区间，禁止随意定义错误码

4. 所有接口必须添加参数校验，入参校验不通过直接返回错误，禁止非法参数进入业务层

#### 3\.1\.4 日志与性能规范

1. 采用结构化日志，统一日志格式，包含时间、级别、链路ID、业务标识、消息内容字段

2. 日志级别分为debug、info、warn、error、fatal五级，生产环境关闭debug级别日志

3. 禁止在循环内执行数据库查询、远程调用等耗时操作；核心接口必须设置超时控制

4. 慢查询、慢接口必须设置阈值告警，定期优化性能瓶颈

#### 3\.1\.5 安全规范

1. 所有外部输入必须做合法性校验，防止SQL注入、XSS、命令注入等攻击

2. 敏感信息禁止明文存储、明文输出，日志中必须脱敏处理

3. 数据库账号、API密钥等敏感配置通过环境变量或配置中心注入，禁止硬编码

4. 接口必须做权限校验，遵循最小权限原则，禁止越权访问

### 3\.2 前端开发规范（Vue 3 \+ TypeScript）

#### 3\.2\.1 工程结构规范

采用Vue 3 \+ TypeScript \+ Vite技术栈，项目目录结构统一为：

```Plaintext
project-root/
├── src/
│   ├── api/          # 接口请求封装
│   ├── assets/       # 静态资源
│   ├── components/   # 公共组件
│   ├── views/        # 页面组件
│   ├── router/       # 路由配置
│   ├── store/        # 状态管理
│   ├── utils/        # 工具函数
│   ├── types/        # TypeScript类型定义
│   └── styles/       # 全局样式
├── public/           # 公共静态文件
├── config/           # 构建配置
└── tests/            # 测试文件
```

组件按业务领域划分目录，公共组件必须具备通用性与可复用性。

#### 3\.2\.2 编码规范

1. 严格遵循TypeScript类型规范，禁止滥用`any`类型，核心业务逻辑必须定义完整类型

2. Vue组件采用`<script setup>`语法，组件命名采用大驼峰命名法，文件命名采用短横线命名法

3. 模板中禁止复杂逻辑表达式，复杂计算必须使用计算属性；避免直接操作DOM

4. 遵循ESLint \+ Prettier代码规范，统一代码风格，启用提交前自动校验

#### 3\.2\.3 状态与路由规范

1. 全局状态采用Pinia管理，按业务模块划分store，禁止跨模块直接修改状态

2. 路由配置采用懒加载模式，按业务模块拆分路由；路由命名统一规范，携带页面唯一标识

3. 路由守卫统一处理权限校验、登录拦截、页面埋点逻辑

4. 组件间通信优先使用props/emit，跨层级通信使用状态管理，禁止事件总线滥用

#### 3\.2\.4 样式与工程化规范

1. 采用SCSS预处理器，全局样式统一管理，组件样式使用scoped隔离

2. 统一设计规范，使用全局主题变量，禁止随意自定义颜色、字体、间距

3. 静态资源按需加载，大图片必须压缩处理，禁止超大资源打包

4. 构建产物按路由分包，优化首屏加载速度；生产构建移除console、debugger代码

#### 3\.2\.5 安全规范

1. 所有用户输入与渲染内容做XSS防护，禁止使用`v-html`渲染不可信内容

2. 敏感信息禁止存储在前端本地，禁止明文传输敏感数据

3. 接口请求统一添加请求拦截器，携带认证信息；响应统一处理异常与权限拦截

4. 前端权限控制仅做界面展示控制，核心权限校验必须在后端执行

### 3\.3 数据库开发规范（MySQL）

#### 3\.3\.1 表结构设计规范

1. 表名采用小写\+下划线命名法，前缀标识业务领域；表名、字段名必须见名知意，禁止拼音缩写

2. 所有表必须包含主键`id`（BIGINT自增或雪花ID）、`create_time`、`update_time`、`is_deleted`四个基础字段

3. 字段类型选择遵循最小够用原则，禁止使用大类型存储小数据；字符串长度合理设置

4. 禁止使用存储过程、触发器、视图；禁止使用外键约束，业务层保证数据一致性

#### 3\.3\.2 SQL编写规范

1. SQL语句关键字大写，表名、字段名小写，缩进统一，提升可读性

2. 禁止使用`SELECT *`，必须明确查询字段；禁止在WHERE条件中对字段使用函数，避免索引失效

3. 多表关联必须控制关联表数量，禁止大表嵌套子查询；分页查询必须设置最大分页限制

4. 批量操作必须控制批量大小，避免一次性操作大量数据导致锁表

#### 3\.3\.3 索引与性能规范

1. 索引创建遵循“按需创建、避免冗余”原则，核心查询字段、关联字段、排序字段建立索引

2. 单表索引数量控制在5个以内，禁止冗余索引、重复索引；联合索引遵循最左前缀原则

3. 慢查询阈值设置为1秒，超过阈值的SQL必须优化；定期执行索引健康检查

4. 生产环境禁止执行DDL、大表DML操作，必须通过发布窗口执行并做好备份

#### 3\.3\.4 数据安全规范

1. 敏感数据（手机号、身份证、密码等）必须加密存储，禁止明文存放

2. 数据库账号按业务分配，遵循最小权限原则，禁止使用超级账号执行业务

3. 生产数据禁止直接导出至开发、测试环境，脱敏后方可使用

4. 数据备份采用全量\+增量结合策略，定期验证备份可用性；删除操作必须软删除

### 3\.4 客户端开发规范（Flutter / 小程序）

#### 3\.4\.1 架构与分层规范

1. 采用分层架构，分为视图层、逻辑层、数据层，各层职责清晰，禁止跨层耦合

2. 页面、组件、工具类按业务模块划分目录，公共组件、通用工具统一沉淀

3. 状态管理采用框架推荐的标准方案，全局状态与页面状态分级管理

4. 网络请求、数据存储、设备能力调用统一封装，禁止业务层直接调用底层能力

#### 3\.4\.2 交互与适配规范

1. 遵循平台设计规范，统一交互模式与视觉风格，保持多端体验一致性

2. 适配主流分辨率与系统版本，兼容低版本系统，禁止出现布局错乱、功能不可用

3. 页面跳转、加载、错误、空状态统一交互逻辑，提供友好的用户反馈

4. 权限调用必须明确告知用户用途，禁止非必要权限申请；权限被拒绝后提供降级方案

#### 3\.4\.3 性能与打包规范

1. 页面按需加载，组件懒加载，避免一次性加载大量资源导致卡顿

2. 图片、资源按需压缩，控制安装包体积；禁止冗余资源、无用依赖打包

3. 内存、CPU占用设置阈值，避免内存泄漏与过度耗电；定期进行性能检测

4. 发布版本必须经过完整测试，禁止带严重缺陷发布；版本号遵循语义化规范

#### 3\.4\.4 安全与合规规范

1. 敏感数据加密存储，禁止明文保存用户信息、认证信息

2. 网络请求采用HTTPS协议，接口数据加密传输；禁止明文传输敏感数据

3. 严格遵守平台合规要求，禁止调用非公开API，禁止违规收集用户信息

4. 第三方依赖必须经过安全审核，禁止引入存在安全风险的组件

## 第四部分 跨领域通用规范

### 4\.1 版本控制规范（Git）

1. 分支管理采用主干开发模式，主干为`main`，开发分支为`dev`，功能分支命名格式为`feature/任务ID-功能描述`，修复分支为`bugfix/缺陷ID-问题描述`

2. 提交信息格式统一为：`类型: 描述`，类型包含feat、fix、docs、style、refactor、test、chore；提交内容必须与描述一致，禁止大杂烩提交

3. 合并代码必须通过Merge Request方式，经过评审与流水线校验通过后方可合并

4. 版本发布打Tag，版本号遵循语义化规范（主版本号\.次版本号\.修订号），留存版本说明

### 4\.2 CI/CD 流水线规范

1. 所有项目必须接入统一CI/CD流水线，包含代码检查、编译构建、单元测试、制品打包、部署发布环节

2. 流水线设置门禁规则，代码检查不通过、测试覆盖率不达标、构建失败禁止进入下一环节

3. 环境部署由流水线统一执行，配置与代码统一版本管理，禁止手动修改环境配置

4. 发布过程全程留痕，支持版本一键回滚；回滚操作必须经过审批并记录

### 4\.3 信息安全规范

1. 代码中禁止硬编码密钥、密码、Token等敏感信息，统一通过配置中心管理

2. 所有系统、环境、账号遵循最小权限原则，定期审计权限，回收冗余权限

3. 第三方组件、依赖库必须经过安全扫描，存在高危漏洞的禁止引入

4. 漏洞修复按分级时限要求执行，高危漏洞24小时内修复，严重漏洞72小时内修复

### 4\.4 文档与交付物规范

1. 研发文档分为过程文档、交付文档两类，统一格式、统一命名、按项目归档

2. 文档版本与项目版本对应，变更同步更新，保证文档与代码一致性

3. 交付物必须包含说明文档、版本记录、校验信息，按标准目录结构归档

4. 知识产权明确，禁止未经授权使用第三方有版权的资源与代码

## 第五部分 规范管理与合规机制

### 5\.1 规范的制定、评审与发布

1. 本规范由信息中心技术委员会负责制定、修订与解释

2. 规范修订必须经过评审流程，征求各业务线意见，审批通过后正式发布

3. 规范发布后同步更新至DSH平台全局规范库，智能体同步加载生效

### 5\.2 版本管理与更新迭代

1. 规范版本采用语义化编号，大版本更新升级主版本号，局部修订升级次版本号

2. 定期评估规范适用性，结合技术演进与业务需求迭代优化；每年至少一次全面评审

3. 规范变更提前公示，明确生效时间，给予项目适配周期

### 5\.3 项目级规范定制规则

1. 项目可根据业务特点制定专属规范，但不得低于本规范的基线要求

2. 项目专属规范必须经信息中心技术委员会审核备案，同步至项目级规范目录

3. 项目规范与全局规范冲突时，以全局规范为准；特殊情况需提交审批

### 5\.4 合规性校验体系

1. 依托DSH平台`verify_env.sh`校验工具，实现规范合规性自动化校验

2. 代码提交、配置发布、产物交付各环节内置规范校验，不合格项拦截

3. 定期开展全项目规范合规审计，输出审计报告，督促问题整改

### 5\.5 审计、考核与持续优化

1. 规范执行情况纳入项目考核与个人绩效评价

2. 建立反馈渠道，收集规范执行中的问题与建议，持续优化完善

3. 推广优秀实践，沉淀为标准规范，提升整体研发水平
